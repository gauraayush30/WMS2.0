## 1. Executive Summary

**ARCHITECTURAL CHANGE:** The current per-product model approach must pivot to a **global per-customer model** at scale. This eliminates model explosion while improving data efficiency and forecast quality.

### The Problem with Per-Entity Models

The original plan proposed: 1 model per (product × customer × warehouse × seller × buyer).  
At scale (400 products × 50 customers × 4 warehouses × 200 sellers × 300 buyers):

- **Per-entity approach**: 8,000,000+ models → impossible to manage, train, version, or monitor
- **Global per-customer approach**: 4,000 models (1 per customer × warehouse) → tractable

### The Right Approach

**1 global model per (customer × warehouse)** that sees ALL products at once, with:

- `product_id` as a categorical feature
- `seller_id` as a categorical feature (nullable for demand forecasts)
- `buyer_id` as a categorical feature (nullable for supply forecasts)

This single model learns "how this customer's business behaves" rather than fragmented signals per SKU. Buyer and seller predictions are generated by running inference with those IDs set, not by loading separate models.

### Portfolio Intelligence Dimensions

The feature answers these questions across the unified model:

| Dimension       | How it's answered                                                      |
| --------------- | ---------------------------------------------------------------------- |
| **By Product**  | Predicted outbound for each SKU (product_id feature in global model)   |
| **By Seller**   | Predicted inbound per seller (seller_id feature in global model)       |
| **By Buyer**    | Predicted outbound per buyer (buyer_id feature in global model)        |
| **Portfolio**   | Aggregated across all products: total supply, demand, risk indices     |
| **By Location** | City/state rolls aggregated from seller origins and buyer destinations |

Exposed through a new **Portfolio** tab in the UI and a cache-based API (no live inference).

## 1.5 Why Global Model? The Scaling Problem

### Model Count Explosion

```
Current approach (per-product):
  Products × Customers × Warehouses = 400 × 50 × 4 = 80,000 models

Expansion plan (per-entity):
  Products × Customers × Warehouses × Sellers × Buyers
  = 400 × 50 × 4 × 200 × 300 = 8,000,000 models ❌

Global per-customer approach:
  Customers × Warehouses = 50 × 4 = 200 models ✓
```

### Data Sparsity Problem

A buyer who ordered 15 times in 90 days cannot support an individual model:

- Too few data points for TimeSeriesSplit CV
- Wild volatility in predictions
- Model retraining instability

**Solution:** Pool those 15 orders into the global customer model alongside every other buyer's orders. The global model sees the aggregate pattern: "this customer's buyers order X units/day on average." Buyer-level predictions then condition on buyer_id, giving the model's learned buyer-specific factor within that aggregate.

### Training & Versioning

- **Per-entity:** 8M models to version, backtest, monitor for drift → impossible at scale
- **Global:** 200 models → manageable, coherent retraining schedule

## 3. Data Model & Linkage Analysis

### 3.1 Existing Key Join Paths

```
INBOUND (Seller → Product):
  inventory_transactions
      ← inbound_lines.transaction_id          (direct FK)
      ← inbound_lines.inbound_id
      → inbound_orders.supplier_id
      → suppliers (name, gstin, address, is_active)
      → seller_locations (name, city, state, zip_code)

OUTBOUND (Product → Buyer):
  inventory_transactions
      ← outbound_picks.transaction_id         (direct FK)
      ← outbound_picks.outbound_line_id
      → outbound_lines.outbound_id
      → outbound_orders.buyer_id
      → buyers (name, gstin, contact_name, delivery_location_id)
      → buyer_locations (name, city, state, zip_code)
```

### 3.2 Transaction Reference Fallback

When `inbound_lines.transaction_id` is NULL (legacy data before the direct FK was added),
fall back to text join:

```sql
inventory_transactions.reference_no = inbound_orders.grn_number
```

Similarly for outbound: `reference_no = outbound_orders.shipment_number`.

### 3.3 Seller-Product Daily Series SQL

```sql
SELECT
    io.supplier_id,
    il.product_id,
    DATE(io.received_at)                     AS date,
    SUM(il.received_qty)                     AS inbound_qty
FROM inbound_lines il
JOIN inbound_orders io ON io.id = il.inbound_id
WHERE io.business_id = :biz
  AND io.customer_id = :cust
  AND io.status      = 'received'
  AND io.supplier_id IS NOT NULL
GROUP BY io.supplier_id, il.product_id, DATE(io.received_at)
ORDER BY date;
```

### 3.4 Buyer-Product Daily Series SQL

```sql
SELECT
    oo.buyer_id,
    ol.product_id,
    DATE(oo.shipped_at)                      AS date,
    SUM(op.qty)                              AS outbound_qty
FROM outbound_picks op
JOIN outbound_lines ol ON ol.id = op.outbound_line_id
JOIN outbound_orders oo ON oo.id = ol.outbound_id
WHERE oo.business_id = :biz
  AND oo.customer_id = :cust
  AND oo.status      = 'shipped'
  AND oo.buyer_id    IS NOT NULL
GROUP BY oo.buyer_id, ol.product_id, DATE(oo.shipped_at)
ORDER BY date;
```

### 3.5 Location-Level Roll-Up SQL

```sql
-- Seller location → city / state aggregation
SELECT
    sl.city,
    sl.state,
    s.id AS supplier_id,
    s.name AS supplier_name,
    il.product_id,
    DATE(io.received_at) AS date,
    SUM(il.received_qty) AS inbound_qty
FROM inbound_lines il
JOIN inbound_orders io  ON io.id = il.inbound_id
JOIN suppliers      s   ON s.id  = io.supplier_id
JOIN seller_locations sl ON sl.supplier_id = s.id  -- lat pick: first active location
WHERE io.business_id = :biz AND io.status = 'received'
GROUP BY sl.city, sl.state, s.id, s.name, il.product_id, DATE(io.received_at);

-- Buyer delivery location aggregation
SELECT
    bl.city,
    bl.state,
    b.id AS buyer_id,
    b.name AS buyer_name,
    ol.product_id,
    DATE(oo.shipped_at) AS date,
    SUM(op.qty) AS outbound_qty
FROM outbound_picks op
JOIN outbound_lines ol  ON ol.id = op.outbound_line_id
JOIN outbound_orders oo ON oo.id = ol.outbound_id
JOIN buyers         b   ON b.id  = oo.buyer_id
JOIN buyer_locations bl ON bl.buyer_id = b.id
WHERE oo.business_id = :biz AND oo.status = 'shipped'
GROUP BY bl.city, bl.state, b.id, b.name, ol.product_id, DATE(oo.shipped_at);
```

### 4.2 Analytics DB Views (Required for Scale)

At 200 customers × 100 products, running seller-product series SQL live is too expensive. Materialized views are **now required** (not optional):

Create in `backend_api/migrations.py`:

```sql
-- Seller-product daily summary (refreshed nightly via background task)
CREATE MATERIALIZED VIEW IF NOT EXISTS mv_seller_product_daily AS
SELECT
    io.business_id, io.customer_id, io.supplier_id AS seller_id,
    il.product_id,
    DATE(io.received_at) AS date,
    SUM(il.received_qty) AS inbound_qty,
    AVG(il.unit_cost)    AS avg_unit_cost
FROM inbound_lines il
JOIN inbound_orders io ON io.id = il.inbound_id
WHERE io.status = 'received' AND io.supplier_id IS NOT NULL
GROUP BY io.business_id, io.customer_id, io.supplier_id, il.product_id, DATE(io.received_at);

CREATE UNIQUE INDEX ON mv_seller_product_daily (business_id, customer_id, seller_id, product_id, date);

-- Buyer-product daily summary
CREATE MATERIALIZED VIEW IF NOT EXISTS mv_buyer_product_daily AS
SELECT
    oo.business_id, oo.customer_id, oo.buyer_id,
    ol.product_id,
    DATE(oo.shipped_at) AS date,
    SUM(op.qty)         AS outbound_qty,
    AVG(op.unit_cost)   AS avg_cogs
FROM outbound_picks op
JOIN outbound_lines ol  ON ol.id = op.outbound_line_id
JOIN outbound_orders oo ON oo.id = ol.outbound_id
WHERE oo.status = 'shipped' AND oo.buyer_id IS NOT NULL
GROUP BY oo.business_id, oo.customer_id, oo.buyer_id, ol.product_id, DATE(oo.shipped_at);

CREATE UNIQUE INDEX ON mv_buyer_product_daily (business_id, customer_id, buyer_id, product_id, date);
```

### 5.2 Buyer-Level Predictions (Via Global Model)

**Goal:** Forecast outbound to each buyer using the global model.

**Approach:**

- No separate buyer_trainer.py
- Call `predict_customer_warehouse(buyer_id=X, product_ids=[...])`
- Global model returns buyer-scoped forecast by setting categorical feature

**Fallback for sparse buyers:**

- If buyer has < 30 historical orders: use `buyer_share × product_model_forecast`
- `buyer_share[buyer, product] = outbound_90d[buyer, product] / sum(outbound_90d[:, product])`

### 5.3 Portfolio-Level Aggregation

No separate computation needed:

```
portfolio_forecast[date] = sum(predict(product_ids=[...], buyer_id=None)[date])
```

Where `buyer_id=None`, the global model sums across all buyers for each product.

## 8. Metrics, KPIs & Insight Definitions

### 8.1 Portfolio-Level KPIs

| KPI                            | Formula                                            | Target        |
| ------------------------------ | -------------------------------------------------- | ------------- | ---------------- | ----- |
| **Forecast Accuracy (WAPE)**   | `Σ                                                 | actual - pred | / Σactual × 100` | < 15% |
| **Model Coverage**             | `products_with_model / total_products × 100`       | > 80%         |
| **Buyer Coverage**             | `buyers_with_model / active_buyers × 100`          | > 60%         |
| **Stockout Rate**              | `products_stocked_out / total × 100` (rolling 30d) | < 5%          |
| **Seller Concentration Index** | `Σ(seller_share²)` (Herfindahl) per product        | < 0.5         |
| **Demand Volatility**          | `std(daily_outbound) / mean(daily_outbound)` (CoV) | Monitor       |
| **Days of Supply (DoS)**       | `current_stock / avg_daily_outbound_7d`            | > 14 days     |

### 8.2 Seller-Level Metrics

| Metric                | Definition                                                     |
| --------------------- | -------------------------------------------------------------- |
| On-Time Delivery Rate | % GRNs received on or before PO expected date                  |
| Average Lead Time     | Mean days from PO creation to `received_at`                    |
| Fill Rate             | `SUM(received_qty) / SUM(expected_qty)`                        |
| Inbound Regularity    | Coefficient of variation of restock intervals                  |
| Share of Inbound      | Seller's fraction of total inbound for each product            |
| Forecast Contribution | How much of product-level inbound forecast is from this seller |

### 8.3 Buyer-Level Metrics

| Metric                | Definition                                    |
| --------------------- | --------------------------------------------- |
| Order Frequency       | Mean days between consecutive orders          |
| Average Order Size    | Mean `outbound_orders.total_qty`              |
| Share of Outbound     | Buyer's fraction of product outbound          |
| Demand Predictability | 1 - CV(order_qty) — higher = more predictable |
| Revenue Concentration | `buyer_revenue / total_revenue`               |
| Reorder Gap Trend     | Is order frequency increasing or decreasing?  |

### 8.4 Date-Range Analytics

All tables and charts support a **global date range picker** at the top of the Portfolio tab.
Default: last 90 days. Options: 7d / 30d / 90d / 180d / Custom.

When a custom range is selected:

1. All API calls include `start_date` and `end_date` query params
2. Backend DB functions filter by date
3. All KPIs recompute for the selected window
4. "vs prior period" delta badges show automatically (prior period = same length before start_date)

## Appendix B — Architectural Decision Record (ADR)

### Decision: Global Per-Customer-Warehouse Model vs. Per-Entity Models

**Date:** 2026-05-09  
**Status:** ADOPTED  
**Supersedes:** Original expansion plan with per-seller and per-buyer models

### Context

The original expansion plan proposed building separate models for:

- Product-level demand (existing)
- Seller-product inbound (new)
- Buyer-product outbound (new)

At scale (400 products, 50 customers, 200 sellers, 300 buyers), this results in 8,000,000+ models — impossible to train, version, monitor, or retrain.

### Problem Statement

1. **Model explosion:** Per-entity approach creates exponential model count; per-customer approach scales linearly.
2. **Data sparsity:** Sparse entities (buyers with <30 orders) have insufficient data for individual models but plenty when pooled.
3. **Training complexity:** Retraining 8M models on a schedule is infeasible; 200 models is tractable.
4. **Versioning drift:** Each model variant requires separate monitoring, backtest, and drift detection.

### Solution

**Build 1 global model per (customer, warehouse)** that:

- Sees ALL products simultaneously
- Uses `product_id`, `seller_id`, `buyer_id` as categorical features (not model boundaries)
- Generates entity-level predictions by conditioning on the categorical feature at inference time
- Stores quantile outputs (P10/P50/P90) in a cache; never runs live inference

### Benefits

| Aspect                  | Per-Entity                   | Global Per-Customer         |
| ----------------------- | ---------------------------- | --------------------------- |
| Model count             | 8,000,000+                   | 200                         |
| Training time per cycle | Months                       | Hours                       |
| Sparse entity handling  | Impossible                   | Pooled signal               |
| Retraining schedule     | Per-entity (async nightmare) | Nightly batch               |
| Forecast quality        | High variance per SKU        | Coherent across product mix |
| Drift monitoring        | 8M models to track           | 200 models to track         |

### Trade-offs

**Loss:**

- No per-entity retraining flexibility (e.g., "retrain Widget A only")
- Categorical feature engineering overhead

**Gain:**

- Manageable at scale
- Leverages pooled data for sparse entities
- Coherent business model (one forecast per business unit)
- Enables portfolio-level insights
